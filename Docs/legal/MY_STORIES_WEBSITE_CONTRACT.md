## Storage and data categories

- **VERIFIED:** Journals use local SwiftData/SQLite in the app sandbox. A journal includes title, rich body, date, creation/modification dates, formatting, tables/checklists, media layout/size and search projections. Selected photo, video and file descriptors include display filename, type, byte count and generated storage identity. Ordinary attachments have managed local files and SwiftData asset payload rows; SwiftData can externalize large payloads into its support directory.
- **VERIFIED:** There is no custom encryption for every journal. Ordinary journals use OS sandboxing and iOS file protection. Individually protected entries use CryptoKit AES-GCM (256-bit keys) and blank their ordinary title/excerpt/search projection columns. Dates and random IDs remain metadata.
- **VERIFIED:** PhotosPicker and file import require explicit selection; no broad photo-library scan or direct camera/microphone capture is implemented. Local import has a 50 MiB limit per attachment. Native Photos may obtain the selected item from the user's Apple-managed library; this is not an app-operated upload.
- **VERIFIED:** Imported original bytes are retained rather than deliberately stripping EXIF/location/camera or video metadata. Rendered thumbnails are downsampled in memory. Do not claim selected originals are metadata-free. Actual picker transcoding/metadata for every source format is **UNVERIFIED**.
- **NOT APPLICABLE:** App-operated location collection, contacts access, advertising IDs, tracking SDKs, analytics SDKs, app accounts, password database, subscriptions and in-app purchase flows in this release. Store price and commercial terms are **OWNER DECISION REQUIRED**.

## Backups, encryption and recovery boundaries

- **VERIFIED:** Ordinary library/store, SQLite WAL/SHM, known SwiftData support directories and managed attachment root are eligible for Apple-managed device backup; the app clears its former exclusion flags. Backup eligibility is not proof that a backup exists or contains the latest content. iOS Settings and the user's backup method control execution and retention.
- **VERIFIED:** Keys use the compatibility Keychain service `com.wisdommedium.wmjournals.writing.keys.v1`, access class `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`, and `.userPresence`; access first evaluates `.deviceOwnerAuthentication`. Face ID/device passcode availability and fallback are managed by iOS. No application-level passcode or account recovery exists.
- **VERIFIED:** No missing key is regenerated to “recover” ciphertext. A backup restored to another device can include encrypted journal data whose device-bound key is unavailable. The UI reports this condition and preserves ciphertext. The accepted implementation permits explicitly confirmed deletion after successful device-owner authentication even if the local key is missing; this does not grant read access or weaken encryption.
- **VERIFIED:** Protected previews use complete file protection, backup exclusion, capability-scoped paths and cleanup on access revocation/startup. Protected media originals remain ciphertext in the attachment tree. Earlier ordinary backups, exported/shared copies and device snapshots are not erased by later locking/deletion.
- **UNVERIFIED:** Physical-device Data Protection, actual same-device and replacement-device restore, passcode removal consequences, real Face ID/passcode failure/cancellation, OS backup inclusion and signed upgrade behavior for the final artifact. Simulator and injected-key tests do not prove these.
- **OWNER DECISION REQUIRED:** Accept the device-bound recovery limitation and communicate it before publication. Portable recovery would require separately designed security work; do not suggest cloud recovery is available.

Apple references checked during the audit: [Keychain authentication](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id), [Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility).

## Deletion, recovery, undo and residual copies

- **VERIFIED (SOURCE AND DISK-BACKED REGRESSION TESTS):** Moving to Deleted Journals preserves the canonical content, media and protection key until explicit restoration or permanent deletion. There is no automatic trash expiration. Restoration increments revision so stale editors cannot overwrite it.
- **VERIFIED (SOURCE AND DISK-BACKED REGRESSION TESTS):** Permanent deletion removes the canonical record and preserves a content-free UUID/date tombstone against stale saves/import resurrection. The hardening collector removes unreferenced SwiftData attachment rows and managed files; shared/trash references, active edits, undo, prepared saves and legitimate recovery copies remain retained. Removed media can be retained while an editor can still undo removal.
- **VERIFIED (SOURCE AND DISK-BACKED REGRESSION TESTS):** Durable key-retirement intent is saved with protected deletion/removal of protection. Cleanup retries at library startup and subsequent collection; Settings offers retry on cleanup failure. Unknown or corrupt reference/recovery data aborts collection to avoid data loss. An interrupted cleanup can temporarily leave bytes pending retry. Pending recovery for a permanently deleted source does not automatically recreate the deleted journal.
- **VERIFIED:** App-controlled thumbnail buffers and renderers have finite lifetimes; native Quick Look, system caches, OS snapshots and user-initiated copies are outside a promise of complete erasure. Explicit protected text copies are local-only with a 60-second pasteboard expiry, but another app may read/copy while available. Ordinary copies use the normal system clipboard. Do not promise clipboard-history erasure.
- **NOT CLAIMED:** Forensic erasure from flash, SQLite free pages/WAL history, existing system backups, screenshots, Photos originals, exported/shared files, Quick Look caches, other devices or third parties. The app does not delete the user's imported source files. Uninstall behavior and Keychain persistence are OS-controlled; uninstall is not a reliable promise to erase every historical copy.

## Network activity, permissions and notifications

- **VERIFIED:** `JournalReleaseFeatures.cloudSyncEnabled` is false. The shipping library opens with `cloudKitDatabase: .none`; iPhone entitlements are empty. Preserved cloud/portable-transfer implementations are inactive. No app-operated upload, account API, remote journal processing, advertising or third-party analytics is present in the audited path.
- **VERIFIED:** Legal links and user-authored links may open a browser. Ordinary file previews use native Quick Look; media uses native playback. A strict claim that no associated OS/browser network activity can ever occur is unsupported. Website hosting, browser requests, server access logs and support email are separate data flows.
- **VERIFIED:** Reminder authorization is requested when the user explicitly enables a local daily reminder. Reminders contain the app name and “Time to write.”, without journal titles/body/media. Disabling cancels the app's pending daily request. Notification-denied state and actual delivery require device validation.
- **VERIFIED:** Face ID usage text describes per-entry protection. The release does not request direct camera/microphone recording or broad Photos permission. Selected files may use temporary security-scoped access.
- **VERIFIED:** Protected content is concealed on inactivity/background and excluded from search/list previews; protected predictive learning/autocorrection restrictions are intentional. Ordinary entries may appear in the App Switcher. Do not claim universal preview concealment.
